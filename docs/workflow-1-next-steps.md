# Workflow 1 — Що далі (практичний план запуску)

Цей документ — продовження до `docs/workflow-1-contract-architecture.md` і відповідає на питання: **що робимо далі, щоб реально запустити Workflow 1 поза n8n**.

## 1) Рішення по відкритих питаннях (до початку розробки)

Прийняти 5 рішень (owner: бізнес + технічний лід):

1. Поведінка `PARTNER_NOT_FOUND`:
   - текст для користувача в Telegram;
   - чи логувати такі запити в окрему таблицю/лог.
2. Поведінка `PARTNER_DUPLICATE`:
   - блокувати та ескалювати, або брати перший запис за правилом.
3. Зберігання PDF:
   - тільки тимчасово в пам’яті, чи архівувати в S3/GCS.
4. Alerting:
   - куди надсилати технічні помилки (Telegram admin / Slack / Email).
5. Джерело текстових шаблонів:
   - hardcoded або конфіг (файл/БД).

**Критерій завершення:** зафіксовані рішення в цьому документі (або ADR).

---

## 2) Мінімальний MVP (етап 1)

MVP має повністю повторити поточну поведінку n8n:

1. Отримати Telegram webhook update.
2. Витягнути `edrpou` із `message.text`.
3. Прочитати 1 рядок із Google Sheets.
4. Згенерувати PDF через APITemplate.io.
5. Надіслати PDF у Telegram.
6. Надіслати друге текстове Telegram-повідомлення.

**Поза MVP:** складна черга, мульти-воркфлоу, UI адміністрування.

---

## 3) План реалізації (технічні кроки)

## Крок 1. Каркас сервісу
- Підняти базовий backend (рекомендовано Node.js + TypeScript + Fastify/Nest).
- Створити endpoint `/webhooks/telegram`.
- Додати health endpoints: `/health/live`, `/health/ready`.

## Крок 2. Інтеграції
- `GoogleSheetsClient`: пошук по `ЄДРПОУ`.
- `ApiTemplateClient`: генерація PDF і повернення `download_url`.
- `FileDownloader`: скачування binary PDF.
- `TelegramClient`: `sendDocument` і `sendMessage`.

## Крок 3. Use-case
- Реалізувати `GenerateAndSendInvoice` з контракту.
- Додати валідацію `edrpou`.
- Додати error mapping → зрозумілі коди помилок.

## Крок 4. Логи та метрики
- Structured logging: `updateId`, `chatId`, `edrpou`, `step`, `durationMs`, `status`.
- Базові метрики: success/fail, p95 latency.

## Крок 5. Тестування
- Unit: мапінг таблиці → DTO, формат повідомлень.
- Integration (mock): Google/APITemplate/Telegram.
- Smoke: тестовий Telegram-чат + тестовий запис у таблиці.

---

## 4) Cutover-стратегія з n8n на сервіс

1. **Shadow mode (1–2 дні):**
   - n8n лишається основним;
   - новий сервіс виконується паралельно без фактичної відправки (dry-run).
2. **Canary (10–20%):**
   - частину запитів переводимо на сервіс;
   - відстежуємо помилки інтеграцій.
3. **Full cutover:**
   - Telegram webhook остаточно перемикаємо на новий сервіс.
4. **Rollback plan:**
   - збережений webhook n8n для швидкого повернення.

- [ ] Всі секрети в env/secret-manager.
- [ ] Налаштовані retries + timeout для зовнішніх API.
- [ ] Є idempotency по `telegram update_id`.
- [ ] Є alerting на критичні помилки.
- [ ] Є інструкція ручного відновлення (runbook).
- [ ] Підготовлений rollback.

## 6) Що потрібно від вас прямо зараз

Щоб перейти до **коду етапу 1**, потрібні:

1. Підтверджені тексти для `PARTNER_NOT_FOUND` і `PARTNER_DUPLICATE`.
2. Рішення, чи зберігаємо PDF після відправки.
3. Обраний стек (якщо не Node.js/TypeScript).
4. Тестові ключі/акаунти (або мок-середовище) для:
   - Telegram bot,
   - Google Sheets доступу,
   - APITemplate.io.

Після цього можна одразу переходити до імплементації сервісу Workflow 1.

## 7) Де переглянути сервіс та протестувати дизайн/функціонал

Нижче практична схема середовищ, щоб було зрозуміло **де саме дивитися сервіс** на кожному етапі:

### A. Локально (швидка перевірка)

- URL сервісу: `http://localhost:3000`
- Перевірка здоров’я: `GET /health/live`, `GET /health/ready`
- Webhook endpoint: `POST /webhooks/telegram`

Для локального тесту Telegram webhook зручно підняти тунель (наприклад, ngrok/cloudflared) і прив’язати webhook бота до публічної URL.

### B. Test/Staging (основне місце для перевірки дизайну і функціоналу)

Рекомендоване окреме середовище:

- `https://invoice-bot-staging.<your-domain>`
- Окремий **staging Telegram bot** (не продакшн-бот).
- Окрема тестова Google Sheet (копія бойової структури з тестовими даними).
- Окремий APITemplate template/API key для тестів.

Саме тут перевіряємо:

1. Функціонал end-to-end (ввід ЄДРПОУ → PDF → 2 повідомлення в Telegram).
2. Тексти/дизайн повідомлень (форматування, читабельність, назва PDF).
3. Обробку edge-cases (`PARTNER_NOT_FOUND`, `PARTNER_DUPLICATE`).
4. Стабільність інтеграцій (retries/timeouts).

### C. Продакшн

- `https://invoice-bot.<your-domain>`
- Тільки після успішного staging smoke/UAT.
- Рекомендовано canary-включення (10–20% трафіку) перед повним cutover.

### Чекліст тестування дизайну та функціоналу

Мінімальний тест-набір перед релізом:

1. **Happy path:** валідний ЄДРПОУ → коректний PDF + коректне текстове повідомлення.
2. **Not found:** неіснуючий ЄДРПОУ → зрозуміле повідомлення користувачу.
3. **Duplicate:** дубль у таблиці → передбачена реакція (за обраним правилом).
4. **Помилка APITemplate:** контрольована помилка + alerting.
5. **Помилка Telegram send:** retry спрацьовує, дублю немає.
6. **Ідемпотентність:** повторний один і той самий `update_id` не дублює відправку.

### Хто і що переглядає

- **Бізнес/оператор:** тексти, коректність реквізитів, зовнішній вигляд PDF.
- **QA/PM:** сценарії та регресія по чеклісту вище.
- **Dev/Ops:** логи, метрики, retry, стабільність інтеграцій, алерти.
